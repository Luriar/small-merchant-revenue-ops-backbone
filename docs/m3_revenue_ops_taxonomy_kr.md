# M3 Revenue Ops 도메인 택소노미 (한국어)

> 문서 버전: v0.1 | 최종 수정: 2026-05-05 | 대상 마일스톤: M3

---

## 1. 프로젝트 정체성

### 1.1 이 시스템이 하는 것

**AI Revenue Ops OS for Small Merchants**는 소상공인이 매출 변화의 **가능성 높은 원인 후보를 근거와 함께 이해**하고, **바로 실행할 액션까지 결정**할 수 있게 돕는 시스템이다.

핵심 기능:

1. **매출 이상 탐지**: 상권/업종 단위 추정매출의 이상 변화를 감지한다.
2. **근거 후보 연결**: 이상 변화와 함께 관측된 외부 요인(수요, 기상, 경쟁 등) 후보를 연결한다.
3. **액션 추천**: 근거 후보에 기반하여 소상공인이 실행 가능한 액션을 추천한다.
4. **Revenue Brief**: 위 내용을 소상공인이 이해하기 쉬운 언어로 요약하여 제공한다.

### 1.2 이 시스템이 아닌 것 (명확한 경계)

| 구분 | 설명 | 이유 |
|------|------|------|
| 상권 분석 대시보드 | 데이터를 시각화만 하는 도구가 아니다 | 판단 지원과 액션 추천이 핵심이다 |
| POS 대체 시스템 | 개별 매장 POS 데이터를 대체하지 않는다 | 공공 추정치 기반이며 상권/업종 단위이다 |
| 인과관계 증명 엔진 | 매출 변화의 원인을 확정하지 않는다 | 상관관계 기반 후보 제시이며, 추가 확인이 필요하다 |
| 매출 보장 솔루션 | 특정 액션의 매출 효과를 보장하지 않는다 | 외부 변수가 많으며 개별 매장 상황에 따라 다르다 |
| 실시간 모니터링 | 초/분 단위 실시간 알림을 제공하지 않는다 | 공공데이터 갱신 주기는 일/주/분기 단위이다 |

## 2. 도메인 용어집

### 2.1 핵심 지리/업종 단위

| 용어 | 정의 |
|------|------|
| **상권 (Trade Area)** | 서울시가 정의한 행정·기능적 경계 단위. 예: 성수역, 홍대입구역 상권. `trade_area_code`로 식별한다. |
| **업종 (Category)** | 서비스 업종 분류. 예: 카페/커피음료, 한식, 편의점. `category_code`로 식별한다. |
| **행정동 (Administrative Dong)** | 행정 목적의 최소 구역 단위. 상권 경계와 완전히 일치하지 않으므로 매핑 과정이 필요하다. |

### 2.2 데이터 단위

| 용어 | 정의 |
|------|------|
| **추정매출 (Estimated Revenue)** | 공공데이터 기반으로 추산한 상권·업종별 분기 매출 총액. 개별 매장 실매출이 아니다. |
| **거래건수 (Transaction Count)** | 해당 상권·업종의 분기 추정 거래 건수. |
| **유동인구 (Floating Population)** | 특정 시간대·장소에 있는 것으로 추정되는 인구. 생활인구의 유사어로 사용한다. |
| **생활인구 (Living Population)** | 서울시가 통신 데이터 기반으로 추정한 유동인구. 주민등록인구와 다르다. |
| **점포수 (Store Count)** | 인허가 기반으로 집계된 업종별 영업 점포 수. 경쟁 환경 지표로 사용한다. |

### 2.3 분석 단위

| 용어 | 정의 |
|------|------|
| **기준 기간 (Baseline Period)** | 비교의 기준이 되는 기간. 예: 2024 Q3. |
| **비교 기간 (Compare Period)** | 분석 대상 기간. 예: 2024 Q4. |
| **변화율 (Change Rate)** | `(비교 기간 값 - 기준 기간 값) / 기준 기간 값`. 음수이면 감소이다. |
| **이상 임계값 (Anomaly Threshold)** | 이상으로 판단하는 변화율 기준값. 기본적으로 -10% 이상 감소를 이상으로 본다. |

### 2.4 파이프라인 단위

| 용어 | 정의 |
|------|------|
| **Bronze 레이어** | 원천 데이터를 변환 없이 보존하는 저장 계층. |
| **Silver 레이어** | 정규화된 신호 스키마 형태로 변환된 계층. |
| **Gold 레이어** | 운영 판단을 위한 마트 계층. 이상 탐지, 근거 후보, 액션 추천이 이 계층에서 생성된다. |
| **이상 탐지 (Anomaly Detection)** | 매출/거래건수의 변화율이 임계값을 초과했는지 판단하는 과정. |
| **근거 후보 (Evidence Candidate)** | 이상과 함께 관측된 외부 요인. 원인이 아니라 후보이다. |
| **액션 추천 (Action Recommendation)** | 근거 후보에 기반한 실행 가능한 대응 방안. |
| **Revenue Brief** | 이상 탐지 결과, 근거 후보, 액션 추천을 소상공인 언어로 요약한 출력물. |

## 3. 이상 유형 분류

### 3.1 이상 유형 정의

| 이상 유형 | 코드 | 조건 | 설명 |
|-----------|------|------|------|
| 매출 감소 | `revenue_drop` | 매출 변화율 < -10% | 추정매출이 기준 기간 대비 10% 이상 감소한 경우 |
| 거래건수 감소 | `transaction_drop` | 거래건수 변화율 < -10% | 거래건수가 기준 기간 대비 10% 이상 감소한 경우 |
| 심각한 매출 감소 | `severe_revenue_drop` | 매출 변화율 < -20% | 추정매출이 기준 기간 대비 20% 이상 감소한 경우 |
| 약한 성장 경고 | `weak_growth_warning` | 0% <= 매출 변화율 < 5% | 외형적으로 증가이지만 경쟁 환경 악화 등 추가 확인이 필요한 경우 |

### 3.2 이상 판정 우선순위

1. `severe_revenue_drop`: 즉각적인 대응이 필요한 최고 우선순위
2. `revenue_drop` + `transaction_drop`: 복합 감소 신호 — 수요 문제로 해석될 가능성이 높다
3. `revenue_drop` 단독: 거래당 매출 감소 가능성 — 단가 문제 또는 믹스 변화 검토 필요
4. `transaction_drop` 단독: 거래건수 감소이지만 건당 매출 유지 — 객단가 분석 필요
5. `weak_growth_warning`: 낮은 우선순위이지만 경쟁 심화 시 주의

### 3.3 샘플 시나리오 이상 판정 (성수 카페 2024 Q4)

```
상권: 성수
업종: 카페/커피음료
기준 기간: 2024 Q3
비교 기간: 2024 Q4

추정매출 변화율: -12%  → revenue_drop 해당
거래건수 변화율: -10%  → transaction_drop 경계값

판정: revenue_drop + transaction_drop (복합 감소)
우선순위: 2순위 — 수요 감소 및 외부 요인 검토 필요
```

## 4. 근거 유형 분류

### 4.1 근거 유형 정의

| 근거 유형 | 코드 | 데이터 소스 | 설명 |
|-----------|------|------------|------|
| 수요 감소 근거 | `demand` | 생활인구 | 상권 내 생활인구가 이상과 함께 감소한 경우 |
| 기상 근거 | `weather` | 기상청 ASOS | 강수일수 증가, 이상 기온 등 기상 변화가 이상과 함께 관측된 경우 |
| 경쟁 근거 | `competition` | 점포수 데이터 | 동일 업종 점포수 증가(경쟁 심화)가 이상과 함께 관측된 경우 |
| 맥락 근거 | `context` | 공휴일, 지역행사 | 공휴일 감소, 대형 행사 종료 등 맥락 변화가 이상과 함께 관측된 경우 |
| 벤치마크/전환 근거 | `benchmark_or_conversion` | 업종 전체 트렌드 | 동일 업종의 서울 전체 트렌드와의 비교를 통해 지역 특이 요인 탐색 |

### 4.2 근거 연결 방식

근거 후보는 이상이 탐지된 후, 동일 기간에 해당 상권/업종에서 관측된 외부 요인을 연결하여 생성한다.

```
revenue_drop 탐지
    ↓
demand_signal 확인: 생활인구 변화율 계산
    → -8% 이상 감소 시: demand 근거 후보 생성
    ↓
weather_signal 확인: 강수일수/기온 변화 확인
    → 강수일 +20% 이상 증가 시: weather 근거 후보 생성
    ↓
competition_snapshot 확인: 점포수 변화 확인
    → 점포수 +5% 이상 증가 시: competition 근거 후보 생성
    ↓
holiday_context 확인: 공휴일 수 변화 확인
    → 공휴일 수 감소 시: context 근거 후보 생성
    ↓
local_event_context 확인: 대형 행사 종료 확인
    → 이전 기간 대비 행사 규모 감소 시: context 근거 후보 생성 추가
```

### 4.3 근거 후보 신뢰도 수준

| 신뢰도 | 코드 | 정의 |
|--------|------|------|
| 높음 | `strong` | 복수의 데이터 소스에서 일관된 방향으로 관측됨. 예: 생활인구 -10% + 강수일 +30% 동시 발생. |
| 중간 | `medium` | 단일 데이터 소스에서 관측됨. 다른 요인과 복합 작용 가능성이 있음. |
| 낮음 | `weak` | 변화 방향이 불일치하거나 데이터 품질 이슈가 있음. 추가 확인이 필요하다. |

## 5. 액션 유형 분류

### 5.1 액션 유형 정의

| 액션 유형 | 코드 | 예시 |
|-----------|------|------|
| 프로모션/할인 | `promotion` | 우천 할인 쿠폰 발행, 계절 한정 메뉴 프로모션 |
| 메뉴 업데이트 | `menu_update` | 계절 메뉴 추가, 고마진 메뉴 강화 |
| 운영 최적화 | `operational` | 우천 시 배달 서비스 강화, 영업시간 조정 |
| 채널 확장 | `channel` | 배달앱 입점, 테이크아웃 프로모션 강화 |
| 고객 유지 | `customer_retention` | 단골 고객 재방문 쿠폰, 멤버십 프로그램 도입 |
| 비용 관리 | `cost_management` | 비수기 인력 최적화, 식재료 발주 조정 |
| 커뮤니케이션 | `communication` | SNS 홍보 강화, 지역 커뮤니티 광고 |

### 5.2 액션-근거 매핑 원칙

액션 추천은 근거 후보 유형에 따라 매핑된다. 근거 없이 액션만 추천하지 않는다.

| 근거 유형 | 우선 고려 액션 유형 |
|-----------|-------------------|
| `demand` (수요 감소) | `promotion`, `customer_retention`, `channel` |
| `weather` (악천후) | `operational`, `promotion`, `channel` |
| `competition` (경쟁 심화) | `menu_update`, `promotion`, `customer_retention`, `communication` |
| `context` (공휴일 감소 등) | `promotion`, `operational`, `communication` |
| `benchmark_or_conversion` | `menu_update`, `channel`, `cost_management` |

### 5.3 샘플 시나리오 액션 추천 (성수 카페 2024 Q4)

근거 후보: demand + weather + competition

```
액션 추천 1 (weather + operational):
  "비 오는 날 배달/테이크아웃 서비스를 강화하는 것이 고객 접근성을 높이는 데 도움이 될 수 있습니다."
  액션 유형: operational + channel
  근거: 강수일수 증가가 함께 관측되었습니다.

액션 추천 2 (competition + promotion):
  "주변 카페 점포수 증가가 함께 관측되었습니다. 단골 고객 재방문을 유도하는 스탬프 카드나 멤버십 프로그램 도입을 검토해보세요."
  액션 유형: customer_retention
  근거: 점포수 증가가 함께 관측되었습니다.

액션 추천 3 (demand + menu_update):
  "유동인구 감소와 함께 관측된 거래건수 감소를 고려할 때, 기존 고객의 객단가를 높이는 시즌 메뉴나 세트 메뉴 강화를 검토해볼 수 있습니다."
  액션 유형: menu_update
  근거: 생활인구 감소가 함께 관측되었습니다.
```

## 6. 신뢰도 수준 정의

### 6.1 신뢰도 계산 기준

신뢰도는 근거 후보의 데이터 품질과 일관성에 기반하여 계산된다.

| 요소 | 가중치 | 설명 |
|------|--------|------|
| 데이터 소스 수 | 높음 | 복수 소스에서 일관된 방향으로 관측될수록 신뢰도 증가 |
| 변화 규모 | 중간 | 변화 규모가 클수록 신호 강도 높음 |
| 데이터 신선도 | 중간 | 최근 데이터일수록 신뢰도 높음 |
| 샘플 크기 | 낮음 | 해당 상권의 데이터 포인트 수 |

### 6.2 신뢰도 수준별 정의

**strong (높음)**:
- 조건: 2개 이상의 근거 데이터 소스가 일관된 방향으로 변화했으며, 변화율이 임계값의 1.5배 이상
- 표현: "복수의 데이터에서 일관되게 함께 관측되었습니다."

**medium (중간)**:
- 조건: 1개 근거 데이터 소스에서 관측되었으며, 변화율이 임계값을 초과
- 표현: "함께 관측되었습니다. 다른 요인과의 복합 작용 가능성도 있어 추가 확인이 필요합니다."

**weak (낮음)**:
- 조건: 데이터가 불완전하거나, 변화 방향이 이상과 일치하지 않거나, 샘플이 적음
- 표현: "데이터가 충분하지 않아 추가 확인이 필요합니다."

## 7. 표현 가이드라인

### 7.1 사용해야 할 표현

Revenue Ops OS의 모든 출력물(Revenue Brief, 근거 후보 설명, 액션 추천 설명 등)에서 아래 표현을 사용한다.

| 상황 | 사용할 표현 |
|------|------------|
| 근거 후보 제시 | "가능성 높은 원인 후보입니다" |
| 상관 관계 설명 | "함께 관측되었습니다" |
| 영향 가능성 표현 | "영향을 주었을 가능성이 있습니다" |
| 불확실성 표현 | "추가 확인이 필요합니다" |
| 추정치 고지 | "공공데이터 기반 추정치입니다" |
| 액션 추천 | "검토해보세요" / "도움이 될 수 있습니다" |

**올바른 표현 예시**:

```
2024년 4분기 성수 카페/커피음료 업종의 추정매출이 2024년 3분기 대비 약 12% 감소한 것으로
관측되었습니다. 동일 기간 강수일수 증가와 생활인구 감소, 점포수 증가가 함께 관측되었으며,
이들이 매출 변화에 영향을 주었을 가능성이 있습니다. 이는 가능성 높은 원인 후보이며,
실제 매장 상황과 함께 추가 확인이 필요합니다.
```

## 8. 데이터 한계 명시 (시스템 전반 적용)

모든 문서, 출력물, API 응답에 아래 데이터 한계를 명시한다.

### 8.1 분석 단위 한계

- 분석 단위: **상권/업종 수준** (개별 매장 수준 아님)
- 매출 데이터: 공공데이터 기반 **추정치** (실제 매출과 다를 수 있음)
- 인구 데이터: 통신 데이터 기반 **추정치** (실제 방문자와 다를 수 있음)

### 8.2 데이터 신선도 한계

- 추정매출: 분기 종료 후 수 주 내 제공 (실시간 데이터 아님)
- 점포수: 인허가 기준이므로 실제 영업 상태와 다를 수 있음
- 기상 데이터: 서울 관측소(지점번호 108) 기준이므로 국지적 차이 존재 가능

### 8.3 인과관계 한계

- 이 시스템은 상관관계를 기반으로 원인 후보를 제시한다.
- 인과관계가 있다고 확정하지 않는다.
- 매출 변화에는 이 시스템이 포착하지 못하는 다양한 요인이 있을 수 있다.
